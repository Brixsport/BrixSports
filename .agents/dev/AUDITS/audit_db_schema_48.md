## 1. Schema drift — `schema.ts` vs live `PRAGMA table_info()`

**Checked:** ran `PRAGMA table_info()` against staging for `matches`, `players`, `teams`, `match_events`, `player_team_affiliations`, `football_player_stats`, `basketball_player_stats`, `standings`, `competition_sport_settings`, `system_settings`, `system_settings_history`, `competitions`, plus `PRAGMA index_list()` on the first seven. Diffed every column name, type, nullability, and default against the corresponding `sqliteTable()` definition in `src/db/schema.ts` (main checkout, current).

**Found: no drift on any of these 12 tables.** Column names, snake_case mapping, nullability, and defaults all match exactly, including the unusual camelCase-in-a-snake_case-schema columns (see §6). This is a materially better result than the brief's framing ("documented history of schema drift... see known-issues.md for several real past examples") suggested is still true today — those past examples (`match_duration` snake/camel mismatch, missing `organizations_slug_unique` index) are dated 2026-06-14/16 and read as **already resolved**: `matchDuration` no longer exists in either `schema.ts` or live (dropped from both, confirmed by diffing the worktree's stale schema, which still has it, against the current one, which doesn't), and `organizations_slug_unique` is present live. **Severity: none — this section is a clean bill of health, not a gap.** Worth stating plainly since a false "drift is still rampant" belief would waste a future session re-auditing something already fixed.

**Not checked at column level (time-boxed out, lower confidence):** `schema-predictions.ts`, `schema-fpl.ts` (11 FPL tables), `schema-xi.ts`, `schema-user-lineups.ts`, `schema-ratings.ts`. All their live tables exist (confirmed via the full live table list, §2) and none showed up as orphaned in the FK checks that touch them, but no `PRAGMA table_info()` diff was run column-by-column for these. If a future audit has budget, this is the next place to look — flagging as unverified, not as a known gap.

## 2. Live tables with no Drizzle definition, and one with an incomplete barrel export

**Checked:** `SELECT name FROM sqlite_master WHERE type='table'` against staging (71 tables, excluding `sqlite_%`/`__drizzle_migrations`... actually `__drizzle_migrations` is included in the 71), then grepped every table name against `src/db/*.ts` for a matching `sqliteTable(...)` call.

**Found — three live tables have zero Drizzle definition anywhere in the codebase:**

- **`logger_sessions`** — created and queried entirely through raw `sql\`...\`` template literals in `src/lib/sessionStore.ts` (`CREATE TABLE IF NOT EXISTS logger_sessions (...)`, called from the constructor on every `DatabaseSessionStore` instantiation). This directly contradicts CLAUDE.md's own Database rule ("No raw SQL strings — use Drizzle query builder only") and is real, live, currently-used code (logger heartbeat/session tracking, not dead). Not schema drift in the "column mismatch" sense — there is no schema to drift from — but it means this table has no type safety, no `drizzle-kit` migration history, and would silently diverge from any future Drizzle-based tooling that assumes `schema.ts` is authoritative. **Severity: low-medium** — works today, but is invisible to anything that introspects `schema.ts` (this audit's own table-drift pass in §1 would never have found a problem here even if one existed, because there's nothing to diff against).
- **`football_player_stats_snapshot_pre_md1_20260709`** — a one-off manual backup table (name is self-documenting: pre-matchday-1 snapshot, 2026-07-09). Not in any schema file, not referenced anywhere in `src/`. **This is genuinely dead/orphaned in the "table nobody reads" sense** — real orphaned-data finding per the brief's request, but it's an intentional backup artifact, not a bug. **Severity: trivial** — safe to leave (it's a rollback point) or drop once its window of usefulness passes; not touched here per findings-only scope.
- **`team_ratings`** — this one is *not* dead. It **is** defined in `src/db/schema-ratings.ts:52` (`export const teamRatings = sqliteTable('team_ratings', {...})`) and is actively used (`src/lib/ratingsService.ts`, `src/app/api/ratings/analytics/route.ts`, `src/app/admin/match-ratings/[id]/page.tsx`). The gap: `src/db/schema.ts`'s bottom barrel-export block (`export { playerRatings, ratingHistory } from './schema-ratings';`, line ~1138) **does not re-export `teamRatings`**. Every real consumer works around this by importing directly from `@/db/schema-ratings` instead of `@/db/schema` (confirmed: `ratingsService.ts:2` — `import { playerRatings, teamRatings } from '@/db/schema-ratings'`). Functionally harmless today since Drizzle table objects don't require the barrel to work with `.select()/.insert()`, but it does mean `teamRatings` is invisible to the `schema` object passed into `drizzle(client, { schema })` in `src/db/index.ts` — so it's silently excluded from the relational query API (`db.query.teamRatings...` would not exist) and from any future tooling that assumes "everything in `schema.ts`'s exports is the whole schema." **Severity: low** — a one-line fix (`export { playerRatings, ratingHistory, teamRatings } from './schema-ratings';`) if ever touched, not attempted here per scope.

## 3. Redundancy

**Checked:** the brief's own cited example (`eye_point_awards` vs `matchEvents`, `known-issues.md` 2026-07-01) against live data, plus a broader look for the same duplicate-source-of-truth pattern.

**`eye_point_awards` — the documented finding is now stale; the table doesn't exist live.** `eyePointAwards` is defined in `src/db/schema-enhanced.ts:247`, but **`schema-enhanced.ts` is not imported by anything in `src/`** (confirmed: `grep -r "schema-enhanced" src/` → zero results) and **`drizzle.config.ts` points only at `./src/db/schema.ts`** — `schema-enhanced.ts` has never driven a real migration. Live table list (71 tables, queried directly) confirms: **no `eye_point_awards` table exists on staging.** The known-issues.md entry describing this as an active duplicate-source-of-truth problem is accurate about the *code* (the table is genuinely defined twice as a concept) but not about *live impact* — there is only one real source of truth for eye-point data today (`match_events.is_eye_point` + aggregate `players.eye_points`, both real, live, and actually written to by `src/app/api/events/route.ts`). **Correction worth making in `known-issues.md` next time it's touched:** the entry should note the table was never actually deployed, so this is dead-schema hygiene (delete `schema-enhanced.ts`, or the `eyePointAwards` export from it), not a live data-integrity bug. **Severity: trivial** (was already trivial; now provably so).

**The pattern does repeat elsewhere, already documented in depth by `audit_player_team_competition_data_47D.md` (§4/§7 of that file) and reconfirmed live here, not re-derived from scratch:** `teams.played/won/drawn/lost/goals_for/goals_against/points` and `standings.played/won/drawn/lost/goals_for/goals_against/points` are two independently-maintained caches of the same conceptual "team record." Live query confirms the drift is real and total, not theoretical:

```
Joga-Bonito: teams.played=0 vs standings.played=3
Wolves FC:   teams.played=0 vs standings.played=3
... (10/10 sampled teams with any standings row show this exact mismatch)
```

`teams.played` etc. default to `0` and are never updated by any live write path (confirmed: no `.update(teams).set({ played: ... })` anywhere in `src/app`) — every team with real match history shows the frozen `0` default while `standings` (itself only updated by a single manual admin POST per §4 below) shows the real number. **Severity: medium, already tracked as `BACKLOG-097`** — not re-filed, cited for corroboration with fresh live numbers.

**No other new instance of the "two tables, one fact" pattern was found** in the tables checked. `player_stats` (generic, sport-agnostic) vs `football_player_stats`/`basketball_player_stats` (sport-specific) looks like a candidate at a glance, but `player_stats` (schema.ts:506) appears to be an older, more generic precursor table — not checked for live row count or write-path activity in this pass; flagging as **worth a follow-up grep**, not asserting a finding.

## 4. Orphaned/stale data, relationship & normalization issues

**Checked:** 14 FK relationships spot-checked live via `LEFT JOIN ... WHERE <parent>.id IS NULL` (the actual orphan-detection method, not just "does a constraint exist").

**Found: zero orphaned foreign keys** across `matches.{home_team_id, away_team_id, competition_id}`, `match_events.{match_id, player_id}`, `players.team_id`, `football_player_stats.player_id`, `basketball_player_stats.player_id`, `standings.team_id`, `player_team_affiliations.{player_id, team_id}`, `transfers.player_id`, `match_logger_assignments.match_id`, `bracket_nodes.match_id`. This is a genuinely clean result — no dangling references anywhere checked. **Severity: none.**

**A real normalization gap, newly found this session: `standings`'s upsert target has no backing unique index.** `src/app/api/standings/route.ts:77-91` does:
```
db.insert(standings).values(newEntries).onConflictDoUpdate({
  target: [standings.teamId, standings.competitionId],
  set: { played: ..., updatedAt: new Date(), ... }
})
```
But live `PRAGMA index_list('standings')` returns exactly one index: `sqlite_autoindex_standings_1`, unique, on `id` only. **There is no unique constraint on `(team_id, competition_id)` anywhere — not in `schema.ts` (no `uniqueIndex()` call on the `standings` table definition), not live.** SQLite requires an `ON CONFLICT (col, col) DO UPDATE` target to match an actual unique index or primary key at the exact column set, or the statement fails at prepare/execution time with "ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint." This route is, per the 47D audit already on file, "the only writer to the `standings` table anywhere in the entire codebase" — if this hypothesis is correct, every real call to it either errors outright, or (if libsql/Turso's SQLite build is more permissive than stock SQLite here) silently degrades to a plain insert and would eventually produce duplicate `(team_id, competition_id)` rows. **Not confirmed by actually calling the route or running the INSERT** (read-only discipline for this audit — the `.env.local` credentials used are real write-capable app credentials, not the read-only MCP token, so no write statement was risked). Live data currently shows **zero duplicate `(team_id, competition_id)` pairs** in `standings` (checked), which is at least consistent with "the route has never successfully double-fired," but doesn't distinguish "it silently no-ops/errors every time" from "it's just never been called twice for the same pair yet." **Severity: medium — recommend a scoped, non-destructive test** (call the route twice for one team/competition on staging, check for either a 500 or a duplicate row) before this is trusted either way; flagged rather than fixed per findings-only scope. **Fix shape, one line, not implemented:** `uniqueIndex('standings_team_competition_unique').on(table.teamId, table.competitionId)` added to `schema.ts`'s `standings` table (with a `db:push` to reconcile the live index), matching the pattern `player_team_affiliations` already uses (`pta_player_team_unique`).

**Denormalized text field, confirmed live, lower severity than it first looked:** `matches.competition` (free-text) vs the joined `competitions.name` (via `matches.competition_id`) differ on 68 of 70 rows — but every sampled mismatch is a **casing difference only** (`"BUSA League Basketball"` vs `"BUSA LEAGUE BASKETBALL"`), not a genuine content drift. Still a real denormalization risk (nothing enforces the two stay in sync going forward, and a case-sensitive `=` comparison anywhere in the codebase against one or the other would silently fail) but not currently manifesting as wrong data shown to a viewer. **Severity: low.**

**`matches.logger_id` vs `match_logger_assignments` — confirmed duplicate-purpose columns, low current impact.** `matches.logger_id` (single text field) is populated on only 1 of 70 live matches; `match_logger_assignments` (the real many-to-many table, supporting multiple loggers per match) covers 3 distinct matches. Two mechanisms for the same relationship exist in the schema; the newer one (`match_logger_assignments`) is clearly the one in active use. `matches.logger_id` reads as a pre-multi-logger-era leftover column. **Severity: trivial** — not causing wrong behavior today (nothing appears to read it as authoritative given the low population), but worth a grep-before-touch note if anyone considers dropping it, since a column being mostly-`NULL` isn't the same as a column being provably unread.

## 5. The "no mutation audit trail" gap

**Confirmed still true for `matches`,** per `SYSTEM_CRITICALITY_MAP.md`'s own Tier 0 structural-gaps list: "Score, status, and period are admin-PATCHable with no record of previous values, actor, or timestamp." No `matches_history`-style table exists live (checked the full 71-table list) and no write path to `matches` logs a before/after diff anywhere in `src/app` (checked `PATCH /api/matches/[id]`, `bulk-update`, `fixtures/[id]`, `events/route.ts` — none write to any audit/history table on a `matches` mutation). `system_settings_history` is confirmed live and working as the one real precedent (16 `system_settings` rows, 21 `system_settings_history` rows — more history rows than current settings, consistent with genuine change tracking over time; `src/app/api/admin/settings/route.ts` correctly writes `updatedBy` + `updatedAt` on every change). **Severity: as already tracked (Tier 0 structural, not re-scored here) — confirmed current, not stale.**

**Checked whether other frequently-mutated tables have the same gap — they do, and two of them are structurally worse than `matches`:**

- **`players` and `teams` have no `updated_at` column at all** (confirmed via live `PRAGMA table_info()` — both tables list `created_at` only; `schema.ts` matches, no `updatedAt` field defined for either table). This is a stricter gap than "unaudited" — it's "not even a last-modified timestamp exists," for two tables that are genuinely, frequently written (`players.rating`/`eyePoints` on every rated event via `src/app/api/events/route.ts:236-264`; admin edits via `PATCH /api/players/[id]`). There is currently no way to answer "when was this player/team last changed, by what" at all, not even unreliably.
- **`football_player_stats`/`basketball_player_stats` — confirmed live, matches `BUG-195`'s own finding exactly, not re-derived, cross-referenced as instructed.** Both tables have `updated_at` but no `created_at` at all (so there's no baseline to compare against even in principle), and `updatePlayerStats()` (`src/app/api/matches/[id]/events/route.ts`) never includes `updatedAt` in its `.set()` calls — confirmed by reading the same function `BUG-195`'s entry cites. Live spot-check: 16/70 `matches` rows show `updated_at === created_at` (i.e., never touched post-insert, or coincidentally updated in the same second as creation) — consistent with, not proof of, the same-class gap; the stronger evidence is `BUG-195`'s own live POST test (`personal_fouls: 9 → 10` with `updated_at` unchanged), which this audit did not re-run (no need — already DB-confirmed same session).
- **`matches` itself is inconsistent, not just absent, on `updated_at`.** The real, current `/api/matches/[id]/events` route (atomic score increments) and the lineup routes (`lineup/route.ts`, `lineup/unlock/route.ts`, `lineup/publish/route.ts`, `admin/match-lineups/[id]/route.ts`) all correctly set `updatedAt: new Date()` on every `matches` write. But the **older, parallel `POST /api/events/route.ts`** (not `/api/matches/[id]/events` — a separate, still-live file) writes `matches.stats` (line 297-299) and `matches.homeScore`/`awayScore` (line 339-341) with **no `updatedAt` in either `.set()` call.** This means `matches.updated_at` is unreliable as a "last touched" signal depending on *which* of two live, parallel event-write endpoints happened to handle a given event — the same "don't trust `updated_at`" lesson `BUG-195` filed for the stats tables applies to `matches` itself, via a different, narrower mechanism (a stale/legacy endpoint missing the field, not the field being universally unmaintained). Not confirmed which of the two endpoints is actually the one live traffic hits today (that's a routing question outside this audit's scope) — flagged as: if `/api/events` (the legacy one) is still reachable and used, `matches.updated_at` has the same platform-wide reliability problem `BUG-195` found for player stats.

**Net answer to the brief's question:** the "`updated_at` doesn't reliably signal staleness" problem is **platform-wide, not isolated to player stats** — it shows up as three different failure shapes: column doesn't exist at all (`players`, `teams`), column exists but the primary writer never sets it (`football_player_stats`/`basketball_player_stats`, per `BUG-195`), and column exists and is usually set but one parallel/legacy write path skips it (`matches`, new finding here). **Severity: Tier 2/3 infra debt, matching the brief's calibration** — none of this blocks a live match, but it means "last updated" cannot be trusted as evidence anywhere in this schema without checking the specific write path first, which is exactly the lesson `known-issues.md`'s 2026-08-04 entry already states in the abstract; this section supplies the concrete "which other tables" answer that entry left open.

## 6. Naming / timestamp convention inconsistencies

**Camelcase columns in an otherwise all-snake_case schema — confirmed live, broader than one table.** `schema.ts` and live `PRAGMA table_info()` agree: the vast majority of every table uses snake_case column names (`home_team_id`, `created_at`, `is_eye_point`, etc.) — standard for this Drizzle setup. Two tables break this convention with a cluster of camelCase columns, confirmed identical live and in `schema.ts`:
- `matches`: `penaltiesEnabledOverride`, `allowDrawsOverride`, `extraTimeEnabledOverride`
- `competition_sport_settings`: `maxSubstitutions`, `allowSubbedOutReentry`, `extraTimeEnabled`, `penaltiesEnabled`, `allowDraws`, `pointsForWin`, `pointsForDraw`

These read as a matched set added together (the override flags on `matches` clearly correspond 1:1 to the base flags on `competition_sport_settings`), so the inconsistency is at least internally consistent with itself — but it's a real deviation from the rest of the schema's naming convention, live, not just in code. **Severity: cosmetic** — doesn't cause a functional bug (Drizzle's `text('maxSubstitutions')` explicit-name form means the ORM and DB agree, just both disagree with the rest of the schema), but worth a note for anyone hand-writing raw SQL against these two tables, since the naming pattern they'd reasonably guess from every other column would be wrong for these seven.

**Timestamp storage format (ms vs seconds) — confirmed live, and dramatically more widespread than `BACKLOG-185` currently documents.** `BACKLOG-185` (filed session 47F) documents exactly 2 affected rows, scoped to `matches`, from one backfill script (`dev/backfill-write-busa-sf-both.mjs`) using `Date.now()` in a raw `@libsql/client` insert. Live re-check this session:

- **`matches`: confirms `BACKLOG-185` exactly as filed** — 2 of 70 rows (`busa-sf-kings-pirates`, `busa-sf-joga-hammers`) store 13-digit millisecond values; all other 68 rows are correct 10-digit seconds.
- **`match_events`: the same bug class, but at a completely different scale — 1,708 of 1,867 rows (91%) store `created_at` in milliseconds, not seconds.** This was not in `BACKLOG-185`'s scope (that entry explicitly says "only confirmed on `matches`... any other raw-SQL script has the same exposure — not checked here"). Traced live: every one of the 1,708 affected rows has `logger_name IS NULL`; every row with a real `logger_name` (`Mariam`, 154 rows; `admin-001`, 5 rows — the genuinely live-logged/admin-authored events) is correctly stored in seconds. This is consistent with the affected rows being the historical BUSA League backfill corpus (dozens of `dev/backfill-write-busa-*.mjs` / `backfill-basketball-*.mjs` scripts exist, writing match history from spreadsheets, not through the live logging UI) rather than anything wrong with the live `POST /api/matches/[id]/events` path itself — the real, current logging code path (confirmed via `src/app/api/matches/[id]/events/route.ts:176`, `createdAt: new Date()`, going through Drizzle's typed column, which does correctly divide by 1000 on write — verified against the installed `drizzle-orm@0.44.7` source, `sqlite-core/columns/integer.cjs`) is not the source of the bad data. **This means `ORDER BY created_at` on `match_events` is unreliable for roughly 9 in 10 rows platform-wide**, not just the 2 stray rows `BACKLOG-185` currently describes — any feature sorting event history chronologically by `created_at` (rather than by logged `minute`/`second`, which are unaffected) would silently misorder most historical events. **Severity: medium** — doesn't affect live-match display (real-time events use `minute`/`second` for ordering, per the codebase's own convention seen in `known-issues.md`'s 2026-07-23 clock-timestamp entry), but is a real, now-confirmed-larger version of an already-filed backlog item. **Recommend updating `BACKLOG-185`'s scope note** to record this `match_events` finding rather than filing a duplicate — same root cause, same fix shape (`Math.floor(Date.now()/1000)` in the raw-SQL backfill scripts, or route them through Drizzle's query builder instead), much larger blast radius than currently documented.
- **`transfers`: 6/6 rows in milliseconds** (100% of the table, though only 6 rows exist). **`news`: 1/3 rows in milliseconds.** Both consistent with the same "raw-SQL backfill/seed script bypassing Drizzle's timestamp conversion" root cause, not independently investigated further given the low row counts involved.
- **`teams`, `competitions`: 0 affected rows** — both correctly all-seconds, for what it's worth as a contrast (these tables are populated mostly through the real app/admin UI, not bulk backfill scripts, which is consistent with the theory that raw-SQL backfill scripts are specifically the vector).

**Id generation scheme:** all tables checked use `text('id').primaryKey()` with application-generated ids (a mix of `nanoid()`-style random strings for user/event data and human-readable slugs for seeded competition/team/match data, e.g. `busa-sf-kings-pirates`). This is consistent across every table checked — no drift or inconsistency found here; noted for completeness since the brief asked about id-generation schemes specifically.
