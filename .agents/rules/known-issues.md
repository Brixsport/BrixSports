2026-06-19 — Logger auth cookie never set (BUG-044) — `POST /api/loggers/auth` returned the JWT in the JSON body only. `getAuthUser()` reads from `authToken` cookie first — no cookie = 401 on every subsequent request, including PATCH match status and POST events. Root cause: treating the JSON response token as sufficient when the server-side auth layer reads from cookies. Fix: always call `response.cookies.set('authToken', token, ...)` before returning from any auth endpoint that issues a token for server-side consumption. Also store in `localStorage` if offline queue needs it — both paths need the token, in different forms.

2026-06-22 — getAuthUser() silently fails for logger sessions (BUG-057) — Logger JWTs carry `{ id, email, role }` but verifyAuth casts to AuthUser which expects `{ userId }` — so authData.userId is undefined. getAuthUser then queries the users table with undefined, finds nothing, returns null → 401 on every logger request despite valid authToken cookie. Fix: normalize `decoded.userId ?? decoded.id` in verifyAuth; branch on role==='logger' in getAuthUser to query loggers table. Pattern: any time two different JWT payloads (admin vs logger) share the same verify path, the downstream DB lookup must branch on role, not assume a single table. Never test auth by checking if login succeeds — test it by checking if a subsequent authenticated request succeeds.

2026-06-19 — Score update condition incomplete for new event types (BUG-047) — Score update used `type.toUpperCase() === 'GOAL' || value`. Client sends `'Penalty'` and `'Own Goal'` — neither matched. `value` is never in the payload. Every Penalty/OG event silently saved to DB without incrementing either score. Additionally, Own Goal reversed: `teamId` is the conceding team, so crediting `isHomeTeam = teamId === homeTeamId` gave the point to the wrong side. Pattern: whenever a new scoring event type is added to the client, the server-side score update condition must be explicitly expanded. Always list all scoring type strings; never assume the existing condition covers new variants.

2026-06-26 — /api/loggers/me existed but was completely inert (BUG-044b) — The endpoint read `x-logger-id` from a request header or query param with zero JWT auth — a pattern left over from the early prototype phase before `getAuthUser` was extended to support logger sessions. Any caller passing the right header could read any logger's profile. Fix: full rewrite using `getAuthUser` + role check. Pattern: whenever `getAuthUser` is extended to support a new role (admin → logger), audit all existing endpoints for that role and replace any legacy auth patterns (header params, query params) that predated the extension.

2026-06-26 — Single picker function serving both sub-OUT and sub-IN (BUG-067) — `getActiveRoster` had no concept of "on pitch" vs "available bench". Bench players who came on mid-match appeared in the sub-OUT picker (who's going off). Data integrity failure: a player could be logged as going off who was never actually on the pitch as a starter. Fix: two explicit functions — `getOnPitchPlayers` (starters − subbed off + subbed on) and `getAvailableBench` (bench − already subbed on − playerComingOut). Each picker must use only its correct pool. Never use a single roster function for pickers with different eligibility semantics.

2026-06-26 — DELETE /events score revert missing PENALTY + OWN GOAL, wrong OWN GOAL direction (BUG-054) — Parent DELETE route condition was `event.value || type === 'GOAL'`. Pattern: whenever new scoring event types are added to the POST path, the DELETE revert path must be updated in the same commit. Always mirror POST scoring logic symmetrically in DELETE. OWN GOAL direction rule: `teamId` = conceding team → invert with `teamId !== homeTeamId`.

2026-06-26 — DELETE /events never decremented playerStats (BUG-060) — Event undo reverted the match score but left `footballPlayerStats`/`basketballPlayerStats` permanently incremented. Pattern: any route that increments stats on write must decrement on delete — these must be implemented together, never left asymmetric.

2026-06-16 — Dropped column name was snake_case in DB but camelCase in schema.ts — `match_duration` in the live DB, `matchDuration` in schema.ts. `ALTER TABLE DROP COLUMN matchDuration` returned SQL_INPUT_ERROR (no such column). 2026-06-16 — SW serves stale HTML with old JS chunk hashes after deploy (BUG-026) — dynamic cache stored HTML pages indefinitely; after deploy, old HTML references chunk filenames that no longer exist on CDN → blank page or broken app on direct URL visit. 2026-06-16 — SW path guard in the wrong layer caused a registration race — `PWAProvider` useEffect tried to suppress `usePWA`'s registration after the fact, but `usePWA`'s useEffect already ran first. 2026-06-16 — SW double-registration from two independent callers — `push-service.ts` called `navigator.serviceWorker.register('/sw-user.js')` independently while `PWAProvider` already registered via `usePWA`. 2026-06-16 — Free-text inputs for canonical enum data caused DB casing drift — college codes (`ColEng`, `Colmans`, `''`) entered by admins via a plain `<input type="text">` instead of a select. 2026-06-16 — `useLiveStandings` emoji fallback (`|| '❓'`) masked null team logos — hook returned a literal emoji string instead of null, so `TeamLogo` received an emoji and tried to render it as a URL. `isValidLogo` rejected it, triggering initials — correct output by accident, but wrong data type. 2026-06-16 — match_events rows with player_id = NULL corrupt playerStats silently (BUG-032) — 39 events exist with no player reference. ## Standing Rules

Standing anti-patterns and constraints: see `CLAUDE.md`.

2026-06-17 — Empty string teamId causes FOREIGN KEY constraint failure on player create — `body.teamId` arrives as `''` when no team selected; DB rejects it as a non-null FK reference. Fix: always coerce `body.teamId || null` before insert. Applies to any optional FK column.

2026-06-17 — players.number is NOT NULL in DB despite nullable intent — schema has `notNull().default(0)` so null is rejected at DB level. Used `body.number ?? 0` as workaround (0 = unassigned sentinel). Real fix: make column nullable via migration (BACKLOG-072).

2026-06-17 — mirror script (UPDATE) silently no-ops when target rows don't exist on prod — `rowsAffected: 0` for all 30 new players because UPDATE finds no matching IDs. New player rows require INSERT not UPDATE. Always check whether target rows exist on prod before writing a mirror script; if new profiles may be absent, build an INSERT-with-skip-existing script instead.

2026-06-17 — UI form required attribute blocks valid partial profiles — Jersey # and Assigned Team marked `required` in HTML prevented BUSALYMPICS-only players (no team, no jersey) from being created, even though the API and DB allow it. Browser enforces HTML required before the request is sent. Prevention: only add `required` to inputs that the server also enforces as required.

2026-06-17 — Backfill script without sport guard (BUG-033) — college affiliation backfill inserted all players with matching college field into football college team IDs, regardless of sport — always join through the player primary team sport before any affiliation INSERT; add AND (primary_team.sport = 'Football' OR no primary team) guard to every college backfill script.

2026-06-17 — Per-match event route missing auth (BUG-034) — /api/matches/[id]/events POST had no getAuthUser() while /api/events (the other event route) was correctly gated. Two routes serving the same function, only one audited — when adding auth to a route, grep for sibling routes at the same resource level (/api/events AND /api/matches/[id]/events) and audit all of them together.

2026-06-17 — loggerId from client body (BUG-034) — event creation accepted loggerId from the request body, allowing any caller to attribute events to any logger — audit fields (loggerId, createdBy, updatedBy) must always be sourced from the verified authUser, never from the request body.

2026-06-19 — Logger had zero service worker coverage (BACKLOG-093) — `usePWA.ts:13-16` blocks `sw-user.js` on `/logger` paths; `src/app/logger/layout.tsx` did not exist so no SW was ever registered for loggers. Result: no offline cache, no background sync, no push. Fix: `src/app/logger/layout.tsx` wraps children in `<PWAProvider swPath="/sw-admin.js" scope="/logger">`. Prevention: any new path added under `/logger` or `/admin` must have an explicit `layout.tsx` with `PWAProvider`. The root layout's SW is always blocked on these paths.

2026-06-19 — sw-admin.js syncMatchEvents() POSTed without auth to a gated endpoint — tokenless events hit BUG-034's now-gated endpoint, returned 401 indefinitely, triggered an infinite background sync retry storm. Root cause: SW background sync fires outside any browser session — no cookie available. Fix: store JWT at queue-write time in the IndexedDB row; skip (continue) any row with no token in syncMatchEvents(). Prevention: any background sync fetch to a JWT-protected endpoint must embed the token in the queued row at write time, not retrieve it at drain time.

2026-06-19 — Start Match and End Match transitioned local state before PATCH resolved (BUG-049) — `transitionStatus('FIRST_HALF')` and `transitionStatus('FINISHED')` both called before the PATCH, with PATCH errors only logged to console. Logger saw "live" / "finished" while DB held the old state. Fix: PATCH first, check `res.ok`, only then call `transitionStatus`. On failure: `alert()` + re-enable button. Prevention: any flow that writes server state AND transitions local UI state must do the server write first and gate the local transition on confirmed success. The pattern applies to every status change, not just Start/End.

2026-06-19 — PATCH /api/matches/[id] accepts any status string from any authenticated logger (BUG-051) — no enum validation on `body.status`, no role restriction. A logger can directly set `status: 'FINISHED'` without going through `handleFinalize`, or corrupt the status field with an arbitrary string. Fix: validate against the allowed enum; restrict loggers to `['LIVE']` only. Prevention: any freeform string field that maps to a constrained domain (status, role, sport) must be validated against an explicit allowlist in the handler — never trust the client to send valid enum values.

2026-06-19 — JWT_SECRET fallback to public string in loggers/auth (BUG-050) — `process.env.JWT_SECRET || 'your-secret-key-change-in-production'` — if env var is absent, all tokens are signed with a known public key. Fix: import from `env.ts`, no fallback. Prevention: never use `||` with a string fallback on any secret value. `env.ts` + `validateEnv()` at startup is the correct pattern; it fails fast instead of silently degrading to an insecure state.

2026-06-22 — AuthContext wipes localStorage.authToken for logger sessions → offline queue gets null token (BUG-058b) — `AuthContext.checkAuth` runs on every page mount. It calls `GET /api/auth/me`, which returns 401 for loggers (admin-only endpoint). On 401, line 74 calls `localStorage.removeItem('authToken')`. FootballLogger's offline catch block reads `localStorage.getItem('authToken')` — gets null — hits the `!token` guard — fires alert instead of queuing. Fix: (1) `POST /api/auth/refresh` now supports logger tokens and returns the new token in the response body; (2) FootballLogger mount effect calls refresh on load and re-writes the token to localStorage, guaranteeing it survives the AuthContext wipe. Prevention: when two components in the same session both touch `localStorage.authToken` — one reading (FootballLogger) and one deleting (AuthContext) — the read must come from a source that outlasts the delete. A cookie-backed refresh call is the durable source.

2026-06-24 — Timeline tab TypeError masked as network 500 (BUG-059) — `LiveMatchTimeline` received `eyePoints` as `undefined` (API never returns that key) and called `.length` unconditionally. Client-side render crash appeared as a failed network request in DevTools — not a server 500. Sentry captures this as a client exception, not a server error log. Prevention: any component prop typed as an array must be guarded with `?? []` if the API response shape does not guarantee the key. When a "500" appears in the network panel, verify it is actually a 5xx HTTP status before assuming server-side throw — render crashes can manifest as network failures on dependent requests.

2026-06-24 — RESOLVED label applied without DB evidence (BUG-047 false close) — BUG-047 was marked RESOLVED on "logger showed 2-3." Logger score is derived from locally-dispatched events, not from `matches.homeScore`/`awayScore`. These can differ. The rule is now codified in CLAUDE.md: for any bug that writes to the DB, evidence must include a DB query result showing actual stored values. UI state, HTTP 201 codes, and absence of console errors are explicitly invalid as sole evidence.

2026-06-24 — Period state is ephemeral — phone refresh during live match resets logger to NOT_STARTED at 0:00 (TD-010) — Period transitions (`handlePeriodEndConfirm`, "Start 2nd Half") only update React `useState`. No server PATCH. DB shows `status: LIVE` but logger reloads with no period context. Public page appears to see a match reset. Elevated to CRITICAL pre-live-match blocker. Fix: `currentPeriod` column on `matches`, PATCH on every transition, read on mount. Prevention: any match state that must survive a browser reload (period, half, status) must be persisted server-side. Local-only state is acceptable only for ephemeral UI (animation, scroll position).

2026-06-24 — footballPlayerStats not rolled back on event DELETE (BUG-060) — `DELETE /api/matches/[id]/events` correctly reverts `matches.homeScore`/`awayScore` but never calls `updatePlayerStats` in reverse. A deleted goal leaves the scorer with a ghost goal in their career stats permanently. Also: Penalty and Own Goal event types hit the score pipeline but not `updatePlayerStats` at all — no stat written for the player who scored them. These are architectural holes in the stats increment model; correct long-term fix is event-sourced recompute from `match_events` on demand.

2026-06-25 — [eventId] route had zero auth — any unauthenticated caller could delete any match event (BUG-071) — `DELETE` and `PATCH` on `/api/matches/[id]/events/[eventId]/route.ts` had no `getAuthUser` call at all. The parent route (`DELETE /api/matches/[id]/events`) had the full auth gate; the individual-event route was written separately and never received it. Additionally the DELETE only reverted GOAL score — PENALTY and OWN GOAL were not handled, and OWN GOAL inversion was wrong (reverted `teamId` team rather than opponent). Fix: mirror parent route's auth gate exactly; fix OWN GOAL inversion (`isHomeTeam = event.teamId !== match.homeTeamId`). Prevention: when a new route file is created for a sub-resource (`[eventId]`), always audit auth parity with the parent route before committing. A shared auth helper is not enough — each route file is independently responsible.

2026-06-25 — Undo button updated local state before DB confirmed (pre-fix pattern) — `handleUndo` called `manager.undoLastEvent()` synchronously, then emitted WS broadcast. No server DELETE was called at all. Score reverted locally, DB kept the event, public page diverged. Fix: make `handleUndo` async, call `DELETE /events/[eventId]` first, gate `undoLastEvent()` on `res.ok`. Pattern: any handler that mutates both server and client state must write server first, gate client update on confirmed success — same rule as BUG-049 (Start Match ghost state). This is the same class of bug.

2026-06-19 — Two parallel IndexedDB implementations, wrong one wired (BACKLOG-058) — `offline-queue.ts` writes to `brixsport-offline.events`; `sw-admin.js` drains `BrixsportAdminDB.pendingMatchEvents`. FootballLogger catch block was `console.error` only — neither DB was written to. Fix: FootballLogger writes directly to `BrixsportAdminDB.pendingMatchEvents`. 2026-06-25 — Match status permanently stuck on LIVE after normal match end (BUG-076) — `handleFinalize` (the only path writing `status: FINISHED`) was guarded by `currentPeriod !== 'FINISHED'`. Period transitions to FINISHED via `handlePeriodEndConfirm`, which re-renders and hides the End Match button before `handleFinalize` can be called. Every match with different scores ended permanently stuck on LIVE. Fix: when `nextPeriod === 'FINISHED' && homeScore !== awayScore`, fold `status: FINISHED` into the same period-transition PATCH. Never split "period reaches FINISHED" and "match status becomes FINISHED" into two separate user actions — they must be atomic for the decisive whistle. ET/Penalties paths are the only exception (period can be FINISHED while match continues to shootout).

2026-06-25 — HAR status=0 ≠ server never received the request — Page navigation during in-flight fetch cancels the response receipt on the client and records status=0 in HAR. The server may have already processed the request. In the KIN vs JOG test, 8 events showing status=0 all appeared in the DB (SW queue resent them after reload, server got 2 copies but idempotently handled them). Do not treat HAR status=0 as evidence of server non-receipt — always verify via DB query.

2026-06-25 — Background Sync API (sync.register) is not supported on iOS Safari — Any offline queue drain that relies solely on `ServiceWorkerRegistration.sync.register()` will silently no-op on all iOS devices. Events write to IndexedDB correctly but never drain automatically. Fix: always implement an `online`/`visibilitychange` page-context drain as the primary trigger; Background Sync is Android-only and should be a secondary fallback.

2026-06-26 — 4xx server rejection on event POST had zero UI feedback (BUG-056) — The `else` branch after `if (res.ok)` in FootballLogger's event POST handler only called `console.error`. A 401 mid-match (token expiry) silently dropped the event with no logger awareness. Fix: always surface 4xx rejections as visible alerts in any logger action path — distinguish 401 (re-login required) from 403 (assignment issue) from generic server error. Never leave a logger-facing error path with only a console.error.

2026-06-26 — Disabled button with no explanation is a UX anti-pattern for admin publish flows (BUG-043) — The Publish Lineups button was disabled when captains weren't set but showed no message. Admin users were confused when 11/11 starters were confirmed. Fix: always render an inline conditional message below disabled publish/submit buttons explaining the unmet condition. Do not rely on the disabled visual state alone.

2026-06-27 — React useState ignores prop updates after mount (BUG-079 Part 2) — Modal component initialises `matchSettings` via `useState(initialMatchSettings ?? defaultMatchSettings)`. Parent fetches settings async and updates the prop after the modal is already mounted — `useState` never re-runs, defaults persist. Fix: `useEffect` that calls `setMatchSettings(initialMatchSettings)` when the prop changes. Prevention: any component that receives async-loaded data as an initial prop must use `useEffect` to sync state, not rely on `useState` initial value alone. This applies to any modal/drawer that opens before data loads.

2026-06-27 — API returns array shape but UI reads it as object (BUG-079 Part 1) — `GET /api/competitions/[id]/match-settings` returns `{ settings: [...] }`. The call site destructured `data.settings` and accessed `.maxSubstitutions` directly — all fields were `undefined`, form showed hardcoded defaults on every open. DB write was always correct; only the read was broken. Prevention: when consuming a GET response, always verify the shape with a console.log or a runtime Array.isArray check before accessing properties. Never assume an API returns a plain object when it could return an array wrapper.

2026-06-27 — displayMinute clamped at regulation ceiling, not real stoppage minute (BACKLOG-110) — `updateDisplayMinute()` uses `Math.min(absoluteMinute, halfDuration)` — stoppage-time events (47') get stamped as `45'`. The clock face is correct (reads `absoluteMinute` via `getFormattedTime()`). The two sources diverged silently. Prevention: `displayMinute` and the clock face must read from the same source. Using separate derivations for "display" and "storage" of the same value is a recipe for silent divergence.

2026-06-29 — filterStartersOnly silently filtered subbed-on players from all non-sub event pickers (BACKLOG-106 real root cause) — `PlayerSelectionModal` had `filterStartersOnly=true` for every non-sub event type. The internal filter `!starterIds.has(p.id)` excluded any player not in the original lineup starters — subbed-on players are never starters, so they were always stripped even though `getOnPitchPlayers` correctly added them to the `players` prop. The picker received the right list and immediately filtered it down to the wrong one. Zero error, zero warning. Prevention: whenever a component receives a pre-filtered list as a prop AND applies its own filtering internally, trace both filter paths. Prop-level filtering and component-level filtering are independent — passing the right players in doesn't mean the right players come out.

2026-06-29 — PWA scope /logger vs /admin — logger layout referenced admin manifest (BUG-075) — `manifest-admin.json` has `start_url: "/admin?source=pwa"`. Logger layout (`src/app/logger/layout.tsx`) referenced this manifest. Installing the PWA from `/logger` on iOS silently installed an app that launched to `/admin` — a page loggers cannot access. Never share a manifest between two app sections that have different entry points. Each distinct user role with a different start URL must have its own manifest file.

2026-06-29 — `decrementPlayerStats` defined in collection route, unreachable from individual-event route (BACKLOG-111 root cause) — `decrementPlayerStats` was added to `events/route.ts` (the `/api/matches/[id]/events` collection route). The undo path calls `DELETE /api/matches/[id]/events/[eventId]` which routes to `[eventId]/route.ts` — a completely separate file. The function was never exported, never imported, never called. Stats were not reverted on any undo. Fix: self-contained `revertPlayerStat` function written directly in `[eventId]/route.ts`. Prevention: when adding a helper to a route file, immediately check whether sibling/child route files need the same capability. A helper function that is not exported is only reachable within that single file — if the feature touches multiple route files, extract to a shared lib or duplicate with intent.

2026-06-29 — Second yellow undo only removed the Red Card, not the triggering Yellow Card (BUG-072) — `handleUndo` read the last event and issued one DELETE. When a second yellow is logged, `MatchStateManager.recordEvent` auto-inserts a Red Card as the next event. Undo removed only that Red Card — the Yellow Card stayed in both DB and local state. Fix: detect `detail === 'Red Card (Second Yellow)'`, find preceding Yellow Card for same player, issue a second DELETE, call `undoLastEvent()` twice. Prevention: any auto-generated event that is inserted in response to another event must have a cascade undo path. If event A always triggers event B, then undoing B must also undo A.

2026-06-29 — Dead route handler silently coexisted with its replacement for 10+ sessions (BUG-054 parent route) — `DELETE /api/matches/[id]/events?eventId` was the original undo endpoint. When `[eventId]/route.ts` was built as its replacement, the old handler was never deleted. It had its own `decrementPlayerStats` helper (not exported, not reachable from any other file) that also silently became dead. Neither TypeScript nor runtime gave any signal — the route was simply unreachable from the UI. Prevention: when superseding a route with a new one, delete the old handler in the same commit. A live handler that nothing calls is a maintenance hazard — it accumulates drift from the real path and misleads future readers.

2026-06-29 — Same "no sub awareness" bug in two separate modals — BACKLOG-106 fixed `PlayerSelectionModal` (general event picker) but `PenaltySequenceModal` had an identical `starterIds`-only check. The root cause (on-pitch status computed from lineup starters only, ignoring subbed-on players) manifested in two independent components. Session 35 fixed one; session 37 found the other. Prevention: when fixing a modal prop/logic pattern, grep for all modals that render player lists and check each one — a pattern bug is usually present at every call site, not just the one that surfaced first.

2026-06-29 — try/catch dropped on stat reversion rewrite, creating false 500 after successful delete — `revertPlayerStat` was written as a clean replacement for `decrementPlayerStats`. The original function had an explicit `// Don't throw — event deletion already succeeded` guard. The rewrite dropped it. Result: any DB error during stat reversion caused the outer try/catch to return 500 — event was already deleted, logger got a false failure. Prevention: when rewriting a function that explicitly swallows errors, the new version must preserve that contract. Search for `// Don't throw` or `// ignore` comments before rewriting — they are intentional, not cleanup targets.

2026-06-30 — httpOnly cookies are invisible in HAR exports — not a missing-cookie bug — HAR specification intentionally omits httpOnly cookies from the `cookies` array. If a fetch returns 401 and HAR shows `cookies: []`, this does NOT mean the cookie wasn't sent — it means the cookie is httpOnly. Check the server-side `request.cookies.get(...)` log, not the HAR. Never file a "cookie not being sent" bug based solely on a HAR with empty cookies.

2026-06-30 — `getAuthUser` logger branch returns null for logger-role users registered via viewer path — `getAuthUser` branches on `role === 'logger'` and queries the `loggers` table. A user who registered via the viewer login path can have `role='logger'` in the `users` table. Their JWT carries their `users` table ID, which is not present in the `loggers` table. The branch returned null (401) instead of falling through to the `users` table. Fix: if loggers-table lookup misses, fall through to users-table lookup. Pattern: any time a role-based lookup can fail for an actor who has that role set in a different table, the lookup must have a fallback — never return null on a single-table miss if the role can exist in multiple tables.

2026-06-30 — Logger cookie bleed into viewer-app routes — `authToken` cookie is set with `path: '/'` (domain-wide). Logger JWTs carry the logger's `loggers` table ID. Viewer-app routes that query `userFavorites`/`userFollows` (keyed to `users.id`) receive a logger ID that matches no user row → empty results. Not a 401 — auth passes but query returns zero rows. Fix: `resolveEffectiveUserId()` bridges the gap by looking up the logger's fan account in `users` by email. Long-term fix is SSO (BACKLOG-117). Until then: every viewer-app route that queries user-scoped data must call `resolveEffectiveUserId()` before the DB query.

2026-07-01 — BUG-084 false filing: "pushSubscriptions always empty, no enrollment UI" — assumption made from an early diagnose endpoint result before any user had onboarded. DB query (2026-07-01) confirmed 3 real subscribers on prod. Enrollment UI exists in SettingsOverlay, OnboardingModal, and NotificationPermission — all three call `PushService.subscribe(userId)`. Never file a table-empty bug without a direct DB count. Never assume a feature is unwired without grepping all call sites of the implementing function.

2026-07-01 — Shared VAPID keys across staging and prod — staging test match delivered a real VAPID push to prod subscribers. Root cause: VAPID private key identical in both Vercel projects + shared Railway WS server emitting `io.emit('notification:global')` to all sockets. Fix: rotate VAPID keys per environment, generate separate JWT_SECRET per environment. Prevention: any key that controls push delivery, token signing, or DB access must be unique per environment. Shared Railway WS compounds the problem — `io.emit` is not room-scoped.

2026-06-29 — console.error in API route does not reach Sentry — assumed Sentry would capture any server-side error. It does not. `console.error` goes to Vercel function logs only. Sentry only captures what is explicitly passed to `Sentry.captureException()` or unhandled exceptions propagating through the global error handler. For swallowed errors (try/catch where you intentionally don't rethrow), always add `Sentry.captureException(error)` explicitly. Prevention: whenever writing a catch block that returns a success response, ask "will this error be visible somewhere?" — if the answer is "Vercel logs", add Sentry.

2026-07-09 — Recompute logic scoped to "the current batch" silently overwrites cross-batch history — a stats-recompute step that counts only the events being inserted RIGHT NOW (not a player's full history) is correct only as long as no player ever appears in two processed batches. The moment they do, the second batch's recompute overwrites the first batch's contribution instead of adding to it — no error, no constraint violation, just a quietly wrong number. This surfaced in the BUSALYMPICS backfill (MD1 g1 used scoped recompute; g2 needed cumulative) and in the process uncovered a second, independent instance of the same root problem already live in production (a one-time global stats zero had wiped a real match's cached stats, since the zero never touched the underlying event history). Prevention: any recompute/aggregate-rebuild step must always source from the full authoritative history (query "all of X's events", not "the events I'm inserting this run"), never from the current operation's local scope. Treat this as a hard rule for any script that derives a stored aggregate from an append-only log.

2026-07-09 — Matching/dedup logic checked for duplicate relationships but not conflicting ones — the player-matching pipeline correctly prevented creating a second identical (playerId, teamId) affiliation row, but had no check for whether a NEW affiliation would conflict with an EXISTING one in the same exclusive category. Club-team affiliation is legitimately multi-valued (a player can be on a club AND a college team at once) — but college affiliation is exclusive (one college per student). Nothing distinguished these categories, so a wrong platform-wide match silently gave one real player two simultaneous college affiliations, with no constraint violation to catch it. Prevention: when a matcher/dedup step creates a new relationship, check not just "does this exact relationship already exist" but "does a CONFLICTING relationship in the same exclusivity class already exist" — and know which categories are exclusive vs. multi-valued before writing the check. Fix shipped as `dev/lib/college-guard.mjs`, wired into both the matcher (flags before human sign-off) and write-script pre-flight (hard abort).

2026-07-09 — Nickname written to the wrong per-team affiliation row makes a player invisible to that team's own roster search (recurred 3x: Mayokun, Olusanya, Ayomiposi Alabi) — `player_team_affiliations.nicknames` is scoped per affiliation row, not global to the player. Writing a nickname meant to help future matching to the WRONG affiliation (e.g. a player's club team instead of their college team) means a team-scoped search for that alias finds zero candidates, falls through to a platform-wide search, and can surface a completely unrelated person (in one case, an inert duplicate player record; in another, a different-sport athlete). `players.jersey_name` is a single global value and is NOT the right fix for "known by a different name in a different team context" — renaming it overwrites the player's real identity everywhere. Prevention: when adding a nickname to help a specific team's matcher find a player, always write it to that exact team's `player_team_affiliations` row, verified by `team_id`, never assume `players.jersey_name` or a nickname on a different affiliation will be visible.

2026-07-09 — Cumulative stat recompute must re-derive from full event history every time, never "add a delta to whatever is currently stored" — a variant of the scoped-recompute bug above, caught in a draft before it ran: computing `shots_on_target` as `existing_stored_value + this_match_contribution` instead of `total('Shot on Target') + total('Goal') + total('Penalty')` from the complete match_events history. The delta-add form is fragile in the same way scoped recompute is — it silently compounds if a script is ever re-run, and it inherits any staleness already present in the stored value instead of self-correcting. Prevention: any script producing a stored aggregate must compute the WHOLE value from source events every time, never increment the previous stored number.

2026-07-11 — `competition_team_entries` UPDATE silently no-op'd because the table had zero rows for the target competition — attempted to seed `group_name` via `UPDATE ... WHERE competition_id = ? AND team_id = ?` for 16 BUSA League teams; every UPDATE returned `rowsAffected: 0`.
